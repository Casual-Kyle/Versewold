# File format, version 1

All JSON is UTF-8. Poem Markdown preserves exact text, including blank lines, indentation, Unicode, and trailing newlines. A poem title belongs to the manifest; the app does not silently add or strip a Markdown heading. The editor currently edits Markdown source directly.

`settings.json`:

```json
{
  "schemaVersion": 1,
  "activeProjectId": "book-1",
  "activePoemId": "poem-1"
}
```

`projects/book-1/project.json`:

```json
{
  "schemaVersion": 1,
  "id": "book-1",
  "title": "Winter verses",
  "poems": [
    {
      "id": "poem-1",
      "title": "First light",
      "file": "poems/poem-1.md",
      "formId": "free-verse"
    }
  ]
}
```

`projects/book-1/poems/poem-1.md`:

```markdown
A small light on the windowsill.
The morning, still becoming.
```

The example text above is original demonstration text. The app starts with no prewritten projects.

The `poems` array determines order within each manuscript group. Optional `sections: [{"id":"part-1","title":"Part I — Autumn"}]` defines ordered parts. Documents can add `sectionId`, `kind` (`poem`, `dedication`, `about`, or `text`), `author`, `composedOn` (`YYYY-MM-DD`), and `updatedAt` (RFC3339). Missing `kind` means poem. Reading order is dedication, unsectioned writing, ordered parts, then author pages. The sidebar and document Details provide ordering/assignment controls. IDs generated by the app are UUIDs. The native boundary accepts only ASCII letters, digits, and hyphens in IDs and requires `poems/<poem-id>.md` paths. Filenames remain stable when titles change, avoiding broken references. Human-readable poem contents remain accessible from any text editor.

All paths above are relative to `%APPDATA%\com.client.versewold\`, the shared Tauri roaming app folder. Copy that entire folder to back up or move manuscripts, forms, preferences, and revision snapshots. `user-settings.json` holds personal appearance/writing settings and the optional author profile; `settings.json` holds current selections. Earlier `showGuidance` and `editorFontSize` fields are accepted for migration and removed from selection settings only after personal preferences load successfully. To change existing files externally, close the app first and preserve the manifest links. An unreferenced Markdown file is preserved but is not auto-imported; Load poems can explicitly add it. There are no delete or garbage-collection commands for manuscripts in this foundation. Flat parts and reordering are supported; nested folders remain planned.

Optional project `authorName` supplies the collection byline, and `manuscript` stores validated page settings from the [shared defaults](../Versewold/src/domain/manuscript/defaults.json). All new version 1 fields are optional for older manifests. [Manuscript/PDF documentation](manuscript-pdf.md) describes page ordering, date semantics, author fallbacks, and layout validation. Portable project copies preserve these fields and remap section identities alongside document identities; poem sidecars preserve document kind/byline/dates, without copying a reference to another project's section.

The optional manuscript `poemSignature` boolean defaults to `true` for older page settings. It controls the author/composition-date signature on the final printed page of each poem. Explicit `false` survives save/load and portable copies; signatures remain generated output and never enter the poem's Markdown.

An optional version 1 `templates` array stores project-scoped form definitions, making portable copies independent of another machine's custom-form library. [Save/load/export](save-load-export.md) documents project copies, poem JSON sidecars, fresh import identities, exact Markdown exports, and combined manuscripts. Poem bodies remain separate `.md` files in every portable copy.

Collection planning adds three optional project fields: `description` (up to 20,000 Unicode characters, including paragraphs/tabs), `intendedTone` (up to 200 characters on one line), and `themes` (up to 50 nonblank single-line strings of up to 80 characters each). Older manifests default to empty planning. Native saves and portable project copies preserve these values. Clearing them removes the optional fields; an empty themes array is omitted. The [collection overview](collection-overview.md) edits these values and renames the existing project `title`, retaining IDs and paths. Planning metadata does not enter poem Markdown or change poem composition/revision dates.

Project `themeDefinitions: [{"id":"theme-home","label":"Home"}]` is the canonical theme vocabulary. Older project `themes` string arrays remain accepted until the first theme edit/assignment migrates them; a project cannot contain both nonempty formats. Optional document fields `tone` (200 characters), `planningNotes` (20,000 characters, including paragraphs/tabs), and `themeIds` (up to 50 unique references into `themeDefinitions`) describe the writing without changing its body or dates. Identity syntax follows the existing ASCII ID rule. Full-project import remaps theme identities with their links; individual poem sidecars carry theme labels, tone, and notes, resolving labels into the destination vocabulary. See [poem planning](poem-planning.md).

`documents` exists only in the frontend/native transport object; it is never written as a JSON copy of the poems. Custom form files follow the separate poetry-form schema described in the research folder.

Changed poems and project manifests also receive [automatic saved-version backups](backups.md) under the app folder's `backups/` directory, retaining 50 readable revisions per file. The native loader reads only the current `projects/` files; backup snapshots are never silently imported or restored. Existing executable-adjacent data is handled by [one-time storage migration](storage-migration.md).
